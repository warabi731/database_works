Q: データベース設計の練習のための架空の要件定義を考えてください  
  
A:もちろんです。データベース設計の練習になるように、**単純すぎず、正規化・ER図・主キー/外部キー・多対多・履歴管理まで考えられる架空案件**を1つ作ります。

## 架空案件：「レンタルスペース予約サービス」

### 1. サービス概要

個人や企業が、会議室・撮影スタジオ・キッチン・イベントスペースなどを時間単位で貸し出せるサービス。

利用者はスペースを検索して予約し、オンラインで利用料金を支払う。

スペースの所有者は、自分のスペースを登録し、料金や営業時間、設備などを管理できる。

---

## 2. 登場人物

### 利用者

* アカウントを作成できる
* スペースを検索できる
* スペースを予約できる
* 予約をキャンセルできる
* レビューを投稿できる

### スペース所有者

* スペースを登録できる
* スペースの情報を編集できる
* 営業時間・予約可能時間を設定できる
* 予約状況を確認できる
* 売上を確認できる

### 管理者

* 利用者を管理できる
* スペースを管理できる
* 予約を確認・キャンセルできる
* 不正なレビューを削除できる

---

# 3. 機能要件

### アカウント

利用者は以下の情報を登録する。

* ユーザーID
* 氏名
* メールアドレス
* 電話番号
* パスワード
* アカウント作成日時

1人のユーザーが、**複数の予約**を行える。

---

### スペース

所有者はスペースを登録できる。

スペースには以下の情報がある。

* スペースID
* スペース名
* 説明
* 所在地
* 住所
* 最低利用時間
* 最大利用人数
* 基本料金
* 公開状態
* 登録日時

1人の所有者が**複数のスペース**を所有できる。

---

### カテゴリ

スペースにはカテゴリを設定する。

例：

* 会議室
* 撮影スタジオ
* キッチン
* イベント会場
* コワーキングスペース

1つのスペースに**複数カテゴリ**を設定できる。

また、1つのカテゴリに**複数のスペース**が所属する。

---

### 設備

スペースには設備を登録できる。

例：

* Wi-Fi
* プロジェクター
* ホワイトボード
* キッチン
* 駐車場
* エアコン

1つのスペースに複数の設備を設定できる。

同じ設備を複数のスペースで利用できる。

---

# 4. 予約

利用者はスペースを指定して予約する。

予約には以下の情報が必要。

* 予約ID
* 利用者
* スペース
* 利用開始日時
* 利用終了日時
* 利用人数
* 料金
* 予約状態
* 予約日時

予約状態は、

* 仮予約
* 支払済み
* 利用済み
* キャンセル

のいずれかとする。

### 制約

* 同じスペースについて、時間が重複する予約はできない
* 利用開始日時は現在日時より後でなければならない
* 利用人数はスペースの最大利用人数以下
* 最低利用時間を下回る予約はできない

---

# 5. 料金

スペース所有者は曜日や時間帯によって料金を変更できる。

例えば、

| 曜日 | 時間帯         |        料金 |
| -- | ----------- | --------: |
| 平日 | 09:00〜18:00 | 2,000円/時間 |
| 平日 | 18:00〜22:00 | 3,000円/時間 |
| 土日 | 09:00〜22:00 | 3,500円/時間 |

また、特定の日だけ料金を変更することもできる。

例：

> 2026年12月24日は通常料金の1.5倍

---

# 6. 支払い

予約が確定すると利用者は料金を支払う。

支払い情報には、

* 支払いID
* 予約ID
* 支払い金額
* 支払い日時
* 支払い状態
* 決済方法

を記録する。

決済方法は、

* クレジットカード
* PayPay
* 銀行振込

など。

1つの予約に対して、**複数回の支払い履歴が発生する可能性がある**ものとする。

---

# 7. レビュー

利用者は、実際に利用したスペースにレビューを投稿できる。

レビューには、

* レビューID
* 投稿者
* スペース
* 予約
* 評価（1〜5）
* コメント
* 投稿日時

を記録する。

### 制約

* 利用済みの予約だけレビューできる
* 1つの予約につきレビューは1件まで
* 自分が利用していないスペースにはレビューできない

---

# 8. お気に入り

利用者は気に入ったスペースをお気に入り登録できる。

例えば、

> ユーザーA → スペース001
> ユーザーA → スペース005
> ユーザーB → スペース001

のような関係になる。

---

# 9. 営業時間

スペースごとに曜日別の営業時間を設定できる。

例：

| 曜日 | 開始    | 終了    |
| -- | ----- | ----- |
| 月  | 09:00 | 22:00 |
| 火  | 09:00 | 22:00 |
| 水  | 09:00 | 22:00 |
| 木  | 09:00 | 22:00 |
| 金  | 09:00 | 23:00 |
| 土  | 10:00 | 23:00 |
| 日  | 10:00 | 20:00 |

ただし、祝日などは個別に休業日を設定できる。

---

# 10. 要件の追加条件

さらに実務っぽくするため、以下も考慮してください。

### ユーザー

* メールアドレスは重複不可
* 退会したユーザーのデータは完全削除せず、退会状態を保持する

### スペース

* 削除されたスペースについても過去の予約履歴は残す
* 非公開にしたスペースは新規予約できない

### 予約

* キャンセルした予約も履歴として残す
* キャンセル日時を記録する
* 予約料金は後からスペース料金が変更されても変わらない

### レビュー

* 投稿後に編集可能
* 編集日時を記録する

---

# 11. データベース設計の課題

この要件をもとに、次の順番で設計してみてください。

### STEP 1：エンティティを洗い出す

まず、

> 「これはテーブルになりそう」

というものを列挙します。

例えば、

* ユーザー
* スペース
* カテゴリ
* 設備
* 予約
* 支払い
* レビュー

など。

**最初から正解を決めず、自分なりに洗い出すのがおすすめです。**

---

### STEP 2：各テーブルの属性を決める

例えば「ユーザー」なら、

```text
users
----------------
id
name
email
phone
password
created_at
withdrawn_at
```

のように考えます。

---

### STEP 3：リレーションを考える

特に以下を考えてください。

* User ── Reservation
* Owner ── Space
* Space ── Category
* Space ── Facility
* User ── Favorite ── Space
* Space ── Reservation
* Reservation ── Payment
* Reservation ── Review

ここで**1対1 / 1対多 / 多対多**を整理します。

---

### STEP 4：中間テーブルを考える

この案件では多対多が複数あります。

例えば、

```text
spaces
   ↑
   |
space_categories
   |
   ↓
categories
```

のような構造が必要になります。

---

### STEP 5：正規化する

例えば、

```text
space
--------------------------------
id
name
category1
category2
category3
facility1
facility2
facility3
```

のような設計にしてはいけない理由を考えてみてください。

---

### STEP 6：ER図を作る

最終的に、

```text
User
 │
 ├────< Reservation >──── Space
 │            │              │
 │            │              ├────< SpaceCategory >──── Category
 │            │              │
 │            │              └────< SpaceFacility >──── Facility
 │            │
 │            ├────< Payment
 │            │
 │            └──── Review
 │
 └────< Favorite >──── Space
```

のような関係を自分で完成させます。

---

## 難易度を上げるなら

この案件は、さらに次の要件を追加するとかなり実践的になります。

**Lv.1**

* ユーザー
* スペース
* 予約

**Lv.2**

* カテゴリ
* 設備
* お気に入り
* レビュー

**Lv.3**

* 料金体系
* 営業時間
* 休業日
* 支払い履歴

**Lv.4**

* クーポン
* キャンセル料
* 領収書
* 売上・手数料
* 月次精算

**Lv.5**

* 予約変更履歴
* 料金変更履歴
* スペース情報の変更履歴
* 論理削除
* 監査ログ

特に**「予約時点の料金をどう保存するか」や「料金変更履歴をどう管理するか」**あたりは、DB設計の良い練習になります。

必要なら次に、この要件を使って**「あなたがDB設計 → 私がレビューする」形式の実践問題**として、あえて答えを隠した課題文にできます。
